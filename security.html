Authentication

CSHUBB uses passwordless magic link authentication powered by Supabase Auth. When you log in, you enter your email and we send a one-time login link. Clicking that link signs you in — no password is ever stored, transmitted, or exposed.

Magic links are single-use and expire after a short window. This eliminates the most common attack vector in credential-based systems: password reuse, brute-force, and credential stuffing attacks simply do not apply.

No passwords stored Single-use tokens Short expiry window Email-verified identity

After clicking the link, Supabase Auth verifies the token and issues a JWT (JSON Web Token) session for the authenticated user. This session is stored securely in your browser and is used for all subsequent API calls.

The JWT contains the user's email and org association but never contains sensitive account data. Every API request to the CSHUBB backend includes this JWT, which Supabase validates server-side on every request.

SSO (SAML, OIDC) integration is on the Enterprise roadmap. During beta, all authentication is via Supabase magic links. Enterprise customers can contact us to discuss custom identity provider integration.

Contact support@cshubb.com for SSO enquiries.

Data Isolation

Every workspace in CSHUBB is scoped to an org_slug — a unique identifier provisioned when your workspace is created. All database tables that contain customer data (accounts, notes, AI history, activity logs) are partitioned by org_slug.

Supabase Row-Level Security (RLS) policies are enforced at the database engine level. This means every SELECT, INSERT, UPDATE, and DELETE query is automatically filtered to only the authenticated user's org. It is architecturally impossible for a query from one workspace to return data from another — even if a bug existed in the application layer.

Database-level RLS enforcement org_slug scoped on every table No cross-org data bleed

Row-Level Security is a PostgreSQL feature that enforces access policies at the storage layer. In CSHUBB, RLS policies are defined so that each authenticated JWT can only see rows where org_slug matches the org in the user's session.

This means even if there was an application-level bug — a forgotten WHERE clause, an incorrect API parameter — the database itself would still return zero rows from another org. RLS is your last line of defence and it operates independently of the application code.

All persistent data is stored in Supabase (PostgreSQL) hosted on AWS infrastructure. Supabase provides encryption at rest for all database storage and encryption in transit via TLS 1.2+ for all connections.

No customer account data is written to client-side localStorage in the production app — all persistent state lives in the database, scoped to your org.

Encrypted at rest (AES-256) TLS 1.2+ in transit AWS-hosted infrastructure
Access Control

New users require a valid invite code to join a workspace on their first login. Invite codes are generated and distributed by workspace admins. Without a valid code, first-time login is rejected — no self-service signup is possible.

Returning users (who already have a record in the workspace) do not need an invite code on subsequent logins. Admins can view all active invite codes, revoke them, and create new ones from the Admin panel.

No open registration Admin-controlled invite codes Instant revocation

CSHUBB has two core roles within a workspace:

  • Admin — full access to all modules, the Admin panel, invite code management, user management, feature flag overrides, org-wide API key policy, webhook management, billing, and bulk delete. The first user to create a workspace is automatically assigned admin.
  • User (Member) — access to modules enabled for their plan (Accounts, Revenue, Pipeline, AI Tools, Import/Export). Cannot access Admin panel, cannot delete accounts, and cannot manage invite codes or billing.

Role assignment happens at login time based on whether the workspace already has any users. Admins can also revoke access for any user.

Admins can revoke any user's access from the Admin → Users panel. Revoked users see a blocked screen on their next login attempt and cannot access any workspace data. Their session token becomes invalid immediately.

The revocation is enforced at the database level — the user's is_suspended flag is set, and RLS policies deny all subsequent data access even if they have a valid JWT.

By default, each email address is associated with a single workspace org. If a user attempts to join a second workspace with the same email, they are shown a conflict warning. The allow_multi_org flag can be enabled by an admin for specific users who legitimately need multi-workspace access (e.g., consultants managing multiple clients).

AI & Data Privacy

When you run an AI tool (e.g., Churn Risk, Account Pulse, QBR Talking Points), CSHUBB constructs a prompt using your account data and sends it to your configured AI provider. The data goes directly from your browser to the AI provider API — it does not pass through CSHUBB servers.

This means:

  • Groq — your data is sent to Groq's API (US-based). Subject to Groq's data processing terms.
  • Claude (Anthropic) — sent to Anthropic's API. Subject to Anthropic's terms. You use your own API key.
  • Gemini (Google) — sent to Google AI Studio API. Subject to Google's terms. You use your own API key.
  • LM Studio — runs 100% on your local machine. No data ever leaves your device. Maximum privacy.

For maximum data privacy, use LM Studio as your AI provider.

Direct browser → AI API (no CSHUBB intermediary) LM Studio: 100% offline option

AI API keys (Groq, Claude, Gemini) are stored in the browser's localStorage on the user's own device and are never transmitted to or stored on CSHUBB servers.

For org-wide key mode (admin-configured), keys are stored in the cs_org_features table in Supabase, scoped to the org, and protected by RLS. Only users within that org can retrieve their org's configured key, and only admins can set or change it.

Individual keys: browser localStorage only Org keys: RLS-protected in database Never logged or transmitted to CSHUBB

AI run history (the inputs and outputs of AI tool runs) is stored in your org's Supabase database, scoped by org_slug and protected by RLS. CSHUBB as a platform operator has admin-level database access for maintenance purposes, but does not actively monitor or analyse individual AI run content.

History is available to all authenticated users within your workspace, and admins can see all runs in the usage logs. You can delete AI history entries from within the app.

Webhooks & Integrations

CSHUBB webhooks support two modes depending on your plan:

  • Basic webhooks (Growth plan) — HTTP POST requests sent to your endpoint. Each webhook has a unique secret token generated at creation time. Pass this token in the Authorization header to verify the source.
  • HMAC-signed webhooks (Pro + Enterprise) — Payloads are signed with HMAC-SHA256 using your webhook secret. The signature is included in the X-CSHUBB-Signature header. Your receiving system can verify the signature before processing the payload, guaranteeing the request originated from CSHUBB and was not tampered with in transit.
HMAC-SHA256 payload signing Per-webhook secret tokens Replay attack prevention

Webhook payloads contain account data as configured for the event type (upsert, create, or update). Payloads are sent as JSON and include account fields like name, CSM, tier, ARR, health score, status, and any custom fields.

Webhook payloads never include user credentials, API keys, or authentication tokens. Only account-level data is transmitted.

Audit Logs & Monitoring

CSHUBB maintains audit logs (available to org admins) covering:

  • User logins and session starts
  • Account create, edit, bulk edit, and delete operations
  • AI tool runs (tool name, provider, timestamp, user)
  • Admin actions (invite code creation/revocation, role changes, feature flag updates)
  • Webhook creation, updates, and deletions
  • Beta requests and approval events
  • Account deletion requests

Audit logs are available on all plans and are scoped to your org only.

CSHUBB uses PostHog for product analytics. Tracking is configured conservatively:

  • Autocapture is disabled — only explicitly tracked events are logged
  • Session recording is disabled
  • Page views and named product events (e.g., AI tool run, account created) are captured
  • No PII (names, emails, account names) is sent to PostHog

Usage analytics within your Admin panel (AI runs per user, accounts count, etc.) are derived from your org's database records, not from PostHog.

No session recording No autocapture EU PostHog endpoint
Infrastructure

The CSHUBB application and database run on:

  • Supabase — PostgreSQL database with built-in RLS, real-time subscriptions, and Auth. Hosted on AWS with automatic backups and point-in-time recovery.
  • Supabase Edge Functions — Serverless functions for server-side operations that require the service role key. The service role key is never exposed to clients.
  • Static hosting — The frontend application is served via CDN with HTTPS enforced.
Supabase / AWS-backed Automatic backups HTTPS enforced Service key server-side only

No. The Supabase service role key (which bypasses RLS) is used exclusively in Edge Functions running server-side. The client-facing application uses only the Supabase anon key, which is subject to all RLS policies.

All privileged operations (e.g., provisioning a new org, sending invite emails, admin overrides) are performed via Edge Functions that validate the caller's JWT before executing any service-role operations.

Your API Keys

Individual mode: API keys are stored only in your browser's localStorage. They are never sent to CSHUBB servers, never logged, and never stored in the database.

Org-wide key mode (admin-set): The admin-configured API key is stored in the cs_org_features record in Supabase, encrypted at rest, scoped by org_slug, and accessible only to authenticated members of that org. CSHUBB does not actively read or log these keys.

In both cases, API keys are used client-side to make direct requests to the AI provider. They do not pass through CSHUBB infrastructure.

Shared Responsibility

CSHUBB is responsible for:

  • Database RLS policy enforcement and correctness
  • Secure authentication infrastructure (magic links, JWT validation)
  • Server-side key management (service role key, Edge Function secrets)
  • Infrastructure security (Supabase/AWS hosting, backups, encryption at rest)
  • Application security (preventing injection, XSS, CSRF)

Your organisation is responsible for:

  • Protecting email accounts used for magic link login
  • Safeguarding browser sessions on shared or public devices
  • Managing invite codes responsibly (not sharing codes publicly)
  • Revoking access promptly when team members leave
  • Protecting AI provider API keys stored in browsers
  • Compliance with applicable data protection regulations (GDPR, etc.) for the customer data you store in CSHUBB

Please report security vulnerabilities responsibly by emailing security@cshubb.com. Do not disclose security issues publicly until we have had a chance to address them.

We aim to acknowledge security reports within 24 hours and provide a resolution timeline within 72 hours. Critical vulnerabilities will be patched as a top priority.
